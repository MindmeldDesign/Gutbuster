3 TRACKS / UPDATED SEP 18 2026 / STATUS: IN PROGRESS

Overview

Why Are.na First

Are.na is scaffolding, not the destination.

It's a cheap way to test whether people actually want this content, organized this way, before investing further in the real product. Three tracks run in parallel from here: populate the Are.na prototype fast (Track A), make it good enough to actually learn from (Track B), and keep building the official Next.js / Airtable app toward launch (Track C).

Airtable is not required for Track A. YouTube metadata can go straight into Are.na through a spreadsheet QA step.

Track A

Content Population

Pipeline:

  1. You send channel or playlist URLs.
  2. A script pulls title, uploader, duration, publish date, thumbnail and description via the official YouTube Data API v3, not a scraper.
  3. It writes a QA spreadsheet, one row per video, with an approve checkbox and a target Are.na page picked from your site map.
  4. You review in Excel, check approve, and assign each video to a page.
  5. A script reads the approved rows and writes populate-data.json, ready to push into Are.na via arena-populate.mjs.
ColumnPurpose
ApproveCheckbox, include this row in the Are.na push
Target pageDropdown pulled from site-map.json
TitleEditable override of the scraped title
Team / Theater / Cut Type / FormOptional, blank by default, kept for a future Airtable import
Why the official API, not a scraper

YouTube's Developer Policies push all automated access through the Data API, not tools like yt-dlp. It's free at this scale and the defensible answer if anyone asks how the catalog was built.

The honest ceiling

No custom video player, no Gutbuster design system, no Gutbuster-specific accounts, no moderation, no SEO Gutbuster owns, no mobile path. Fine, even ideal, for testing whether the content lands. Not a foundation to keep building on past that test.

Milestone shape: nest every page, populate through Track A, run metrics on a regular cadence, and put it in front of real improv-community testers, not just friends. The output of this track is a decision, not a launch.

Track C

Official Product

This track does not wait on Are.na. The two tracks test different things: Are.na tests whether people want this content, organized this way; the Next.js app tests whether the real product works end to end.

Sequenced by what unblocks a real demo fastest:

  1. Ship what already works, GitHub push and a Vercel deploy, so the current build is demoable at all.
  2. Watch page, the core interaction still missing.
  3. NavBar routing + Team/Theater pages, makes the site navigable past the homepage.
  4. Polish, Spotlight row, Runtime field, Date display.
  5. Comments, stays v2, deliberately last, it also depends on accounts that don't exist yet.
Special edition

Video Hosting

Gutbuster doesn't host video today, in either track, and shouldn't for the foreseeable roadmap. Airtable's Embed URL field and Are.na's blocks both point at video hosted elsewhere. That's a deliberate choice to keep making, not a gap to close.

Embedding a video via its original platform's player reads as linking to it, not copying it, the same posture as Letterboxd linking to a streaming service. Re-hosting a copy would need real rights clearance from every theater and team, and is genuinely expensive at any real traffic.

The honest exception

If Gutbuster secures a direct relationship with a theater to be the first-party home for its archival footage, self-hosting (Mux or Cloudflare Stream) becomes a real, differentiated feature: the archive, not just a directory of links. A business-development milestone, not an engineering task to schedule.

Ask the clerk

Q&A

Why prototype in Are.na instead of just finishing the real app faster?

"Can we build this" is already answered, the Next.js app proves that. The open question is whether improv fans actually want to browse a site organized this way, and Are.na tests that for near-zero engineering cost.

What's the legal exposure of showing other people's video?

Embedding video hosted by its original uploader is a curated directory, closer to linking than publishing. Re-serving copies would need explicit rights clearance, which is exactly why hosting stays embed-only.

Is scraping YouTube for metadata against their Terms of Service?

In spirit, yes. YouTube's Developer Policies push automated access through the official Data API, not scraping tools. That's why Track A is built on the official API rather than yt-dlp, even though yt-dlp works.

Why Airtable and not a real database?

Airtable rate-limits at 5 requests/second per base with a 30-second lockout past that. It was the right call to move fast without a backend. At real scale it becomes a real constraint, not a hypothetical one.

What's the moat? Anyone could copy an Are.na channel structure.

Correct, and that's fine, nothing about Are.na is meant to be defensible. It's disposable scaffolding. Whatever works gets rebuilt as the proprietary, designed official product.

How does content migrate out of Are.na later?

The same API that populates it reads it back out. Relational fields the official schema needs, Team, Theater, Show, Cut Type, aren't native to Are.na blocks, and should be carried forward as block metadata rather than reconstructed by hand.

What if Are.na itself changes pricing or its API, or goes away?

A real risk of building on someone else's platform, worth naming plainly. The mitigation: the QA spreadsheet, not Are.na's UI, is the source of truth for what's been curated, so nothing unique lives only inside Are.na.
